# 管理者ユーザー管理・ログイン機能 実装仕様書

この仕様書は、既存Webサイトに管理者向けCMS機能を追加するための実装方針です。GitHub
Copilotが既存コードを調査し、段階的に安全に実装できるようにまとめています。

## 1. 現在の状況と方針

### 既にできていること

-   最初の管理者ユーザーを作成する仕組み
-   管理者がログインする仕組み

### 今回の目標

管理者アカウントの管理機能と、ログイン状態・セッションを安全に扱う機能を実装する。

### Copilotへの基本指示

作業開始前に、必ずリポジトリ構成、既存ログイン処理、初期管理者作成処理、DBスキーマ、依存パッケージ、環境変数、`.gitignore`
を確認すること。

-   既存実装を理解してから変更する。理由なく全面的に書き換えない。
-   既存の技術スタック・命名規則・設計に合わせる。
-   不明な仕様は勝手に決めず、必要なら質問する。
-   変更前に、変更・追加するファイルと目的を提示する。
-   小さな単位で実装し、その都度テストする。
-   パスワード、セッション秘密鍵、メール認証情報などをGitに登録しない。
-   DB変更は既存データを壊さないマイグレーションで行う。
-   エラー応答やログにパスワードなどの機密情報を出さない。

## 2. 管理者ユーザー管理機能

  機能               内容                                         優先度
  ------------------ -------------------------------------------- --------
  管理者一覧         登録済み管理者を一覧表示                     高
  管理者追加         権限を持つログイン済み管理者が追加           高
  管理者情報変更     表示名・メールアドレスなどを変更             高
  パスワード変更     ログイン中の管理者が自分のパスワードを変更   高
  管理者削除         不要な管理者アカウントを削除                 高
  アカウント無効化   削除せずログインを禁止                       中
  権限管理           管理者ごとに操作範囲を制限                   中
  最終ログイン日時   最後にログインした日時を記録                 低

### 管理者管理の注意点

-   管理者管理APIは、サーバー側で認証・認可する。画面でボタンを隠すだけでは不十分。
-   自分自身を削除・無効化できるか明確にする。
-   最後に残った有効な管理者を削除・無効化できないようにする。
-   誤操作や監査のため、削除より無効化（論理削除）を優先する設計も検討する。
-   メールアドレスの重複はDB制約とサーバー側検証の両方で防ぐ。
-   誰でも使える公開管理者登録APIは作らない。追加は認証・認可された管理画面からのみ行う。

## 3. ログイン・認証関連機能

  -------------------------------------------------------------------------------------------------------
  機能                       内容                                                 優先度
  -------------------------- ---------------------------------------------------- -----------------------
  ログアウト                 サーバー側セッションを破棄                           高

  ログイン状態確認           セッションが有効か確認するAPI                        高

  ログイン試行制限           短時間の連続試行を制限                               高

  セッション有効期限         一定時間後に再ログインを要求                         高

  パスワード変更時の再認証   現在のパスワードを確認                               高

  セッション無効化           パスワード変更・無効化時などに既存セッションを終了   高

  CSRF対策                   外部サイトからの意図しない操作を防ぐ                 高

  パスワードリセット         本人確認後に再設定                                   中

  二要素認証                 パスワード以外の要素でも本人確認                     中

  ログイン履歴               ログイン日時や成否を記録                             中
  -------------------------------------------------------------------------------------------------------

### セキュリティ要件

既存の認証方式を確認し、それに合わせて実装する。サーバー側セッション方式の場合、少なくとも以下を確認する。

-   ログイン成功時にセッションIDを再生成し、セッション固定攻撃を防ぐ。
-   本番環境のCookieには `HttpOnly` と `Secure` を設定する。
-   `SameSite` はサイト構成に合わせて設定する。
-   セッションの有効期限とアイドルタイムアウトを設定する。
-   ログアウト時はサーバー側セッションを破棄し、Cookieも無効化する。
-   本番環境ではHTTPSを使う。
-   CSRF対策で状態変更リクエストを保護する。
-   ログイン試行はIPアドレスと正規化したアカウント識別子の両方で制限し、アカウント識別子は平文で保存しない。正当な利用者を締め出すほど厳しい制限にしない。
-   ログイン失敗時に、メールアドレスの登録有無を推測できない応答にする。
-   パスワードはArgon2idなどの適切なパスワードハッシュで保存する。平文保存は禁止。
-   パスワード変更・アカウント無効化などの後は、必要に応じて既存セッションを無効化する。
-   パスワードリセットを作る場合、一度だけ使える短時間有効なトークンを使い、DBにはトークンのハッシュを保存する。
-   パスワード、セッションID、リセットトークンをログに記録しない。

## 4. 管理画面の構成案

``` text
管理画面
├── ダッシュボード
├── 管理者管理
│   ├── 管理者一覧
│   ├── 管理者追加
│   └── 管理者情報変更
├── アカウント設定
│   ├── 自分のプロフィール
│   ├── パスワード変更
│   └── ログイン履歴
└── ログアウト
```

各画面の役割： - **ダッシュボード**：CMS管理機能への入口。 -
**管理者一覧**：表示名、メールアドレス、権限、有効・無効、最終ログイン日時を表示。 -
**管理者追加**：新しい管理者アカウントを作成。 -
**管理者情報変更**：表示名、メールアドレス、権限、有効状態などを変更。 -
**アカウント設定**：ログイン中の管理者自身の情報を変更。 -
**ログイン履歴**：権限に応じて履歴を確認。 -
**ログアウト**：サーバー側セッションを終了。

## 5. データベース設計案

既存の `admins`
テーブルを調査し、不足項目だけをマイグレーションで追加する。既存テーブルを安易に削除・再作成しない。

### admins テーブル案

  カラム          用途                       備考
  --------------- -------------------------- --------------------------
  id              管理者ID                   主キー
  email           ログイン用メールアドレス   UNIQUE制約
  password_hash   パスワードハッシュ         平文保存禁止
  display_name    管理画面に表示する名前     必要に応じてNULL可
  role            管理者権限                 権限設計を決めてから導入
  is_active       アカウントが有効か         無効ならログイン不可
  created_at      作成日時                   
  updated_at      更新日時                   
  last_login_at   最終ログイン日時           ログイン成功時に更新

### admin_login_logs テーブル案

  カラム            用途
  ----------------- ----------------------------------------------------------
  id                ログ履歴ID
  admin_id          対象管理者ID。該当管理者がいない場合を記録するならNULL可
  attempted_email   試行時のメールアドレス。保存の必要性を検討
  success           成功・失敗
  ip_address        接続元IPアドレス。保存目的・期間を検討
  user_agent        ブラウザ等の情報。保存目的・期間を検討
  created_at        試行日時

ログイン履歴には個人情報・セキュリティ情報が含まれ得る。保存目的、閲覧権限、保存期間を決める。パスワードやセッションIDは記録しない。

## 6. API設計案

以下は機能整理のための案。実際のURL・HTTPメソッドは既存ルーティングに合わせ、既存APIと重複する場合は既存仕様を優先する。

### 認証API

  メソッド   パス案                        内容
  ---------- ----------------------------- ----------------------------------------
  POST       `/api/auth/login`             ログイン
  POST       `/api/auth/logout`            ログアウト
  GET        `/api/auth/me`                ログイン中の管理者情報・認証状態を取得
  POST       `/api/auth/change-password`   パスワード変更

### 管理者管理API

  メソッド   パス案              内容
  ---------- ------------------- ------------------------------
  GET        `/api/admins`       管理者一覧
  POST       `/api/admins`       管理者追加
  GET        `/api/admins/:id`   管理者詳細
  PATCH      `/api/admins/:id`   管理者情報変更
  DELETE     `/api/admins/:id`   管理者削除。無効化方式も検討

### ログイン履歴API

  メソッド   パス案                    内容
  ---------- ------------------------- ------------------------------
  GET        `/api/admin-login-logs`   権限に応じたログイン履歴取得

すべての管理者管理APIでサーバー側の認証・認可を行う。リクエストから送られた
`admin_id` や `role`
をそのまま信用せず、セッションなど信頼できる認証情報から操作主体を特定する。

## 7. 実装順序

### フェーズ1：認証の基本機能

1.  ログアウト
2.  ログイン状態確認API
3.  未ログイン時の管理画面アクセス制御
4.  セッション有効期限・Cookie設定
5.  CSRF対策
6.  ログイン試行制限

完了条件： - ログアウト後に保護されたAPIへアクセスできない。 -
セッション期限切れ後は再ログインが必要。 -
未ログイン状態では管理画面のデータを取得できない。 -
状態変更APIがCSRF対策で保護されている。 - ログイン試行制限が動作する。

### フェーズ2：管理者管理

1.  管理者一覧
2.  管理者追加
3.  管理者情報変更
4.  管理者の無効化・再有効化
5.  管理者削除（必要性を確認して実装）

完了条件： - 権限のないユーザーは管理者管理APIを利用できない。 -
メールアドレスの重複を防止できる。 - 最後の有効な管理者を失わない。 -
無効化された管理者はログインできない。 -
変更内容がDBに正しく反映される。

### フェーズ3：アカウント設定

1.  自分のプロフィール変更
2.  現在のパスワードを確認したうえでのパスワード変更
3.  必要に応じて既存セッションを無効化

完了条件： - 現在のパスワードが正しい場合だけ変更できる。 -
新しいパスワードは安全な方式でハッシュ化される。 -
変更後は仕様に応じて再ログインが必要になる。

### フェーズ4：運用・追加セキュリティ

1.  ログイン履歴
2.  パスワードリセット
3.  二要素認証
4.  権限の細分化

必要性と運用負荷を確認してから追加する。

## 8. テスト項目

### 認証

-   正しいメールアドレス・パスワードでログインできる。
-   誤ったパスワードではログインできない。
-   未登録メールアドレスでも、登録有無を推測しにくい同等のエラー応答になる。
-   ログアウト後に保護されたAPIへアクセスできない。
-   セッション期限切れ後に保護されたAPIへアクセスできない。
-   ログイン試行制限が機能する。
-   CSRF対策が有効である。
-   無効化された管理者はログインできない。

### 管理者管理

-   管理者一覧を取得できる。
-   権限のない利用者は一覧・追加・編集・削除を実行できない。
-   同じメールアドレスの管理者を重複作成できない。
-   管理者を追加・変更できる。
-   無効化された管理者はログインできない。
-   最後の有効な管理者を削除・無効化できない。
-   存在しない管理者IDには適切なエラーを返す。

### パスワード変更

-   現在のパスワードが誤っている場合は変更できない。
-   正しい場合だけ変更できる。
-   DBには新しいパスワードのハッシュだけが保存される。
-   変更後は古いパスワードでログインできない。
-   必要に応じて既存セッションが無効化される。
