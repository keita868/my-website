# ニュース・お知らせ管理機能 実装設計書

## 1. 目的

管理者が管理画面からニュースやお知らせを入力し、その内容をデータベースに保存できる機能を作る。新規投稿の作成・DB登録に加え、保存済みの下書きを公開できるようにする。編集・削除・一般公開ページへの表示は後続対応とする。

## 2. 今回の実装範囲

### 実装する

1. 管理画面にニュース・お知らせの新規投稿フォームを用意する。
2. 投稿種別（ニュース／お知らせ）、タイトル、本文を入力できる。
3. 下書きまたは公開を選択できる。
4. サーバー側で認証・権限確認・入力検証を行う。
5. 問題がなければデータベースへ登録する。
6. 登録結果を画面に表示する。
7. 登録済み投稿を一覧で確認できるようにする。
8. 投稿一覧から下書きを公開できるようにする。

### 後回しにする

- リッチテキストエディタ
- 公開ページ側のデザイン・検索
- カテゴリの自由な追加・管理
- アクセス解析

### 新規投稿フォーム

| 項目 | UI案 | 必須 | 内容 |

画像（JPEG/PNG/WebP/GIF）とPDFを添付できる。1投稿あたり最大5件、1ファイル5MiBまでとし、サーバー側でファイル署名を検証する。管理画面では画像をプレビューし、PDFを添付リンクとして表示する。

## 5. データベース設計

### テーブル名：`updates`

ニュースとお知らせは別テーブルに分けず、`type`カラムで区別して1つのテーブルに保存する。共通項目が多く、一覧表示や検索がしやすいため。

| カラム | SQLite型の例 | 必須 | 用途 |
|---|---|---:|---|
| id | INTEGER PRIMARY KEY | ○ | 投稿ID |
| type | TEXT | ○ | `news`または`notice` |
| title | TEXT | ○ | タイトル |
| body | TEXT | ○ | 本文 |
| status | TEXT | ○ | `draft`または`published` |
| published_at | TEXT | - | 公開日時。下書きならNULL |
| scheduled_at | TEXT | - | 予約公開日時（UTC）。未予約ならNULL |
| created_by | INTEGER | ○ | 作成した管理者ID |
| updated_by | INTEGER | ○ | 最後に更新した管理者ID |
| created_at | TEXT | ○ | 作成日時 |
| updated_at | TEXT | ○ | 更新日時 |
| revision | INTEGER | ○ | 本文・公開状態の版番号。既存投稿は0から開始し、編集・公開状態変更時に増加 |

### 制約・ルール

- `type`は`news`または`notice`のみ許可する。
- `status`は`draft`または`published`のみ許可する。
- タイトルと本文は空文字・空白だけの入力を許可しない。
- `created_by`と`updated_by`は管理者テーブルのIDを参照する外部キーにする。
- 下書きの場合、`published_at`はNULLにする。
- 予約中の投稿は`status = 'draft'`かつ`scheduled_at`が未来の投稿として保存する。公開後は`scheduled_at`をNULLにする。
- 新規投稿を公開状態で登録した場合、`published_at`はサーバー側で設定する。
- 日時はUTCで保存し、表示時に日本時間などへ変換する方針を推奨する。
- DB側にもCHECK制約やNOT NULL制約を設定し、アプリ側の検証だけに依存しない。
- 添付ファイルのメタデータは`update_attachments`に保存し、実ファイルは非公開のアップロードディレクトリに保存する。

SQLiteを使っている場合のDDL例（実際のDB・既存テーブル名に合わせて調整すること）：

```sql
CREATE TABLE updates (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  type TEXT NOT NULL CHECK (type IN ('news', 'notice')),
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('draft', 'published')),
  published_at TEXT,
  scheduled_at TEXT,
  created_by INTEGER NOT NULL,
  updated_by INTEGER NOT NULL,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (created_by) REFERENCES admins(id),
  FOREIGN KEY (updated_by) REFERENCES admins(id),
  CHECK (length(trim(title)) > 0),
  CHECK (length(trim(body)) > 0)
);
```

このSQLはSQLite用の例。既存の`admins`テーブル名・主キー名、DBの種類、マイグレーション方式を確認してから適用する。既存テーブルを削除・再作成しない。
予約中の投稿は`status = 'draft'`のまま`scheduled_at`を設定し、サーバー側の定期処理で公開する。

## 6. API設計案

実際のURLやHTTPメソッドは既存ルーティング規則に合わせる。

### 新規投稿登録

`POST /api/admin/updates`

リクエスト例（添付ファイルがない場合はJSON、添付する場合はmultipart/form-data）：

```json
{
  "type": "notice",
  "title": "メンテナンスのお知らせ",
  "body": "いつもご利用いただきありがとうございます。...",
  "status": "published"
}
```

`status`には`draft`、`published`、`scheduled`を指定する。`scheduled`の場合は日本時間の`scheduledAt`も送信する。添付フィールド名は`attachments`。

サーバー側の処理順序：

1. 管理者としてログイン済みか確認する。
2. 投稿作成権限があるか確認する。
3. セッションCookie認証の場合はCSRFトークン等を検証する。
4. リクエスト形式と入力値を検証する。
5. `type`と`status`が許可された値か確認する。
6. タイトル・本文の空白や最大文字数を検証する。
7. 作成者IDはリクエストから受け取らず、認証済みセッションから取得する。
8. `published`の場合だけ、公開日時をサーバー側で設定する。
9. DBに登録する。
10. 登録結果を返す。

成功レスポンス例：

```json
{
  "success": true,
  "update": {
    "id": 12,
    "type": "notice",
    "title": "メンテナンスのお知らせ",
    "status": "published",
    "published_at": "2026-11-13T11:00:00.000Z"
  }
}
```

パスワード、セッション情報、内部エラーなどはレスポンスに含めない。

### 投稿一覧取得

`GET /api/admin/updates`

登録内容を管理画面で確認するために実装する。下書きと公開済みの両方を取得し、作成日時の降順で返すことを基本とする。

### 下書きの公開

`POST /api/admin/updates/:id/publish`

ログイン済み管理者とCSRFトークンを検証し、対象が下書きの場合だけ公開状態へ変更する。公開日時・更新日時はサーバー時刻、更新者は認証済み管理者から設定する。存在しない投稿は`404`、下書き以外の投稿は`409`を返す。公開済み投稿の取り下げは対象外とする。

### 投稿の編集・削除・公開取り下げ

- `GET /api/admin/updates/:id`で投稿と添付情報を取得する。
- `PATCH /api/admin/updates/:id`でタイトル・本文・種別・予約日時を更新し、新しい添付ファイルを追加する。
- `DELETE /api/admin/updates/:id`で投稿と添付ファイルを削除する。
- `DELETE /api/admin/updates/:id/attachments/:attachmentId`で添付を削除する。
- `POST /api/admin/updates/:id/unpublish`で公開済み投稿を下書きへ戻す。
- 添付ファイルの取得はログイン済み管理者に限る。
- `GET /api/admin/updates/attachments/:attachmentId/file`で添付を取得する。画像はインライン表示、PDFはダウンロードとする。

各変更APIでは認証とCSRFトークンを検証する。予約投稿はサーバー側の定期処理が予定時刻到達後に公開する。

投稿取得・一覧のレスポンスには整数の`revision`を含める。管理画面の編集PATCHは、読み込み時の値を`X-Update-Revision`ヘッダーに10進整数で送信する。サーバーの現在の版と異なる場合は`409`を返し、本文と追加添付を保存しない。形式が不正な場合は`400`を返す。旧APIクライアントとの互換性のためヘッダー省略は受け付けるが、その場合は編集画面を開いてから保存開始までの他者の変更を検出できない。

`revision`は本文編集・公開・公開取り下げ・予約自動公開で増加する。添付ファイル単独の削除では増加しない。編集中に添付を削除しても、本文の入力内容と読み込み時の版番号を保持する。版の競合時は入力を残し、内容を控えてから最新の投稿を読み直すよう案内する。

### 投稿詳細取得（任意）

`GET /api/admin/updates/:id`

一覧だけで十分なら後回しでよい。編集機能を追加するときに必要になる。

## 7. 入力検証と安全性

- フロントエンドだけでなく、必ずサーバー側でも入力検証する。
- `type`と`status`は許可リスト方式で検証する。
- タイトルと本文の最大文字数を決め、フロントエンド・バックエンド両方で制限する。
- SQLはプレースホルダーを使ったパラメータ化クエリで実行する。
- タイトル・本文は原則テキストとして扱い、表示時に適切にエスケープする。
- 未検証の投稿本文を`innerHTML`等で直接挿入しない。XSS対策を徹底する。
- 将来Markdown入力に対応する場合は、変換後HTMLをサニタイズしてから表示する。
- 管理者APIはサーバー側で認証・認可する。画面を非表示にするだけの制御にしない。
- セッションCookie認証なら、状態変更APIにCSRF対策を適用する。
- DBエラーの詳細やSQL文を利用者に返さない。
- 送信中は保存ボタンを無効化し、二重クリックによる重複登録を防ぐ。
- 通信エラー時は入力内容を保持し、登録済みか不明なまま連続送信しないようにする。

### 本文の扱い

初期実装では本文をプレーンテキストとして保存・表示する方式を推奨する。改行は安全な方法で反映する。将来Markdownエディタを導入する場合も、生成HTMLを無害化してから表示する。「管理者が入力した内容だから安全」と判断しない。

## 8. 登録処理の流れ

```text
管理者が新規投稿画面を開く
        |
        v
種別・タイトル・本文・公開状態を入力
        |
        v
「下書き保存」または「公開する」を押す
        |
        v
フロントエンドで簡易入力チェック
        |
        v
POST /api/admin/updates
        |
        v
サーバー側でログイン状態・権限・CSRFを確認
        |
        v
サーバー側で入力値を検証
        |
        v
作成者ID・日時を認証情報とサーバー時刻から設定
        |
        v
データベースへINSERT
        |
        v
登録成功レスポンス
        |
        v
画面に成功メッセージを表示
        |
        v
投稿一覧を再取得して登録内容を表示
```

## 9. エラー時の画面動作

| 状況 | 画面での対応 |
|---|---|
| タイトル未入力 | タイトル欄にエラー表示 |
| 本文未入力 | 本文欄にエラー表示 |
| 文字数上限超過 | 対象欄に上限を表示 |
| ログイン切れ | ログイン画面へ誘導 |
| 権限不足 | 権限がないことを表示 |
| 通信エラー | 入力内容を保持し、再送信できるようにする |
| DB登録エラー | 一般的なエラーを表示し、詳細はサーバーログに安全に記録 |
| 登録成功 | 成功メッセージを表示し、一覧に反映 |

## 11. 実装順序

### フェーズ1：DBとバックエンド

1. 既存DB・管理者テーブル・マイグレーション方式を確認する。
2. `updates`テーブルを追加するマイグレーションを作る。
3. 管理者認証を要求する投稿登録APIを作る。
4. 管理者認証とCSRF検証を要求する下書き公開APIを作る。
5. サーバー側入力検証を実装する。
6. 投稿一覧取得APIを作る。
7. APIのテストを行う。

### フェーズ2：管理画面

1. 投稿一覧画面を作る。
2. 新規投稿フォームを作る。
3. フォーム入力値をAPIへ送信する。
4. 下書き保存と公開登録を実装する。
5. 投稿一覧から下書きを公開する操作を実装する。
6. 成功・失敗メッセージを表示する。
7. 登録・公開後に一覧を更新する。

### フェーズ3：動作確認

1. ニュースを下書き登録できる。
2. お知らせを下書き登録できる。
3. ニュースを公開状態で登録できる。
4. お知らせを公開状態で登録できる。
5. 登録内容がDBに保存される。
6. ページを再読み込みしても一覧に残る。
7. 未ログインでは登録APIを利用できない。
8. 不正な`type`・`status`や空のタイトル・本文を拒否する。
9. SQLインジェクションやXSSにつながる入力を安全に扱う。
10. 二重クリックで意図しない重複登録が起きない。
11. 下書きの公開で公開日時・更新者が記録され、再度の公開操作は拒否される。
12. 予約時刻に達した投稿が自動公開される。
13. 添付は許可形式・件数・サイズを検証し、ログイン済み管理者だけが取得できる。
