# 九州工業大学交響楽団 Webページ

九州工業大学交響楽団の公式Webサイトの制作・管理用リポジトリです。

- HTML/PHPによる複数ページ構成
- TypeScriptによるフロントエンド実装
- 次の世代の団員が編集しやすい管理者用ページの整備（予定）

### 管理画面（開発用）

バックエンドにはNode.js 22以降が必要です。管理者アカウントは一般公開の登録フォームから作らず、最初に次のコマンドで作成してください。

```bash
# 依存パッケージをインストール
npm install --prefix backend

# このターミナルで使うセッション秘密鍵を生成（本番では環境変数・シークレット管理機能で設定）
export CMS_SESSION_SECRET="$(openssl rand -hex 32)"

# 表示名・メールアドレス・パスワードを対話入力（パスワードは画面に表示されません）
npm --prefix backend run admin:create

# 管理画面を起動
npm --prefix backend start
```

`http://localhost:3000/admin/login` からログインできます。SQLiteのDBとセッションは `backend/data/` に作られ、Git管理対象外です。ローカル開発では同じターミナルで秘密鍵を設定して起動してください。本番環境ではHTTPSを必須とし、`NODE_ENV=production` と十分に長い `CMS_SESSION_SECRET` を設定します。TLS終端プロキシ経由で動かす場合に限り `TRUST_PROXY=1` も設定してください。

管理者セッションは30分間操作しないと失効し、操作を続けていてもログインから8時間で再ログインが必要です。この期限管理の導入前に作成されたセッションも再ログインが必要になります。パスワード変更時の確認は、同じ管理者について端末・接続元をまたいで15分間に10回までです。試行回数制限は現在サーバープロセスのメモリで管理するため、複数プロセスで運用する場合は共有ストアへの変更が必要です。

リポジトリ全体を静的ファイルの公開ディレクトリとして配信しないでください。特に`backend/`（DB・セッション・添付の保存先を含む）、`.git/`、環境変数ファイルをWebサーバーから公開しない構成にし、管理画面と`/api`はExpressへ転送します。`TRUST_PROXY=1`を使用する場合は、Expressへ直接外部接続できないようにし、プロキシ側でクライアント由来の転送ヘッダーを適切に上書きしてください。

初回に作成した管理者には`superadmin`権限が付与されます。以後の管理者追加・権限変更は管理画面の「管理者管理」から行います。通常の管理者は自分のプロフィールとパスワードのみ変更できます。DBスキーマは起動時に`backend/migrations/`の追加マイグレーションで更新され、既存の管理者データは保持されます。

管理画面の「更新情報管理」では、ニュース・お知らせの作成・編集・削除、公開の取り下げ、予約公開を利用できます。画像（JPEG/PNG/WebP/GIF）とPDFを1投稿あたり5件、各5MiBまで添付できます。一般公開ページへの表示は未対応です。

バックエンドの認証・管理APIテストは次のコマンドで実行できます。

```bash
npm --prefix backend test
```

## 👥 開発ガイドライン

本リポジトリで作業するメンバーは、以下のルールに従ってください。

### 1. 日常ワークフロー

| 手順 | 操作 | 内容 |
| --- | --- | --- |
| 1. 準備 | `git checkout main`<br>`git pull origin main` | 作業前に最新の `main` を取り込む |
| 2. 分岐 | `git checkout -b feature/機能名` | 作業用ブランチを作成する |
| 3. 開発 | （コードの編集・ビルド） | ローカルで実装と動作確認を行う |
| 4. 記録 | `git add .`<br>`git commit -m "種別: 変更内容"` | 適切な粒度でコミットする |
| 5. 送信 | `git push origin feature/機能名` | 作業ブランチをGitHubへプッシュする |
| 6. 申請 | `Compare & pull request`（GitHub上） | プルリクエストを作成してレビューを依頼する |
| 7. 統合 | `Merge pull request`（GitHub上） | 問題がなければ `main` にマージする |
| 8. 同期 | `git checkout main`<br>`git pull origin main` | ローカルの `main` を最新に戻す |

### 2. コミットメッセージの規則

メッセージは `種別: 変更内容` の形式で書きます。

| 種別 | 用途 | 例 |
| --- | --- | --- |
| `feat:` | 新機能の追加 | `feat: お問い合わせフォームのバリデーション追加` |
| `fix:` | バグ・表示崩れの修正 | `fix: スマホ表示時のヘッダー崩れを修正` |
| `docs:` | ドキュメントの更新 | `docs: READMEに運用ルールを追記` |
| `style:` | 見た目の調整（コードの意味に影響なし） | `style: インデントの整理と不要なログ削除` |
| `refactor:` | リファクタリング | `refactor: PHP共通パーツの読み込み処理を最適化` |

### 3. 禁止事項・注意事項

| やってはいけないこと | リスク | 対策 |
| --- | --- | --- |
| `main` への直接push | テスト未完了コードの混入、他メンバーの作業破壊 | 必ず `feature/` ブランチを切り、PR経由でマージする |
| 強制プッシュ（`git push -f`） | 他メンバーのコミット履歴や作業を破壊する | 絶対に使用しない |
| 機密情報のコミット | APIキーやパスワードが外部に漏洩する | `.gitignore` で確実に除外する |
| ビルド生成物の直接編集 | `js/main.js` 等はコンパイル時に上書きされて消える | 必ず `src/ts/` 側のソースを修正する |
| 未コミットでのブランチ移動 | コンフリクトや作業内容の消失につながる | こまめにコミットするか `git stash` を活用する |

## 📝 次の世代の方へ

このサイトは、毎年メンバーが入れ替わる中でも更新を続けられることを目指しています。

- 内容を更新するときは、まず上のワークフローに沿ってブランチを切ってください
- 管理者用ページのパスワードはなるべく1年に1回は更新するようにお願いします。
- 困ったときは先輩や過去のPR・コミット履歴を見ると、変更の経緯がわかります
